# Ya-Da Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Ya-Da, a hosted Hebrew/RTL web app that tracks monthly tuition
payments for Dalia's art studio, shows the user what's missing at a glance,
captures payments (via a Morning/GreenInvoice webhook or manual entry), and
imports the existing roster/payment history from the user's Google Sheet.

**Architecture:** Next.js (App Router, TypeScript) on Vercel, with Supabase
(Postgres) for data and Clerk (Google sign-in only) for auth. Due/paid status
is computed from `children` + `child_prices` (effective-dated) +
`receipt_lines`, never stored directly. UI is built from the existing Ya-Da
design system (tokens + `yd-*` CSS classes), ported into real React
components, with two corrections: copy addresses the user (not Dalia), and
pricing uses "full price/discount" instead of "new/continuing".

**Tech Stack:** Next.js 14+ (TypeScript, App Router), Supabase (Postgres,
`@supabase/supabase-js`), Clerk (`@clerk/nextjs`), Vitest + React Testing
Library for tests, plain CSS (design-system tokens as CSS variables + the
`yd-*` component classes) — no Tailwind/CSS framework layered on top.

**Spec:** `docs/superpowers/specs/2026-11-04-yada-design.md`

## Global Constraints

- Dates in the UI: `ddmmyyyy`, no separators (e.g. `05112026`).
- Week starts Sunday everywhere a calendar/date-picker appears.
- Hebrew, RTL throughout: `<html lang="he" dir="rtl">`.
- All Hebrew UI copy phrased as an instruction to the user uses the feminine
  grammatical form (the user is female) — e.g. "סמני", never "סמן".
- Copy addresses the user (the operator), never Dalia — no Dalia-facing
  voice or screens in this phase.
- Pricing uses "full price / discount" framing, never "new/continuing"
  (חדש/ממשיך) labels.
- A month's due amount is always the price in effect for that specific
  month (effective-dated `child_prices`), never the child's current price
  applied retroactively.
- Currency: `₪` after the number with a space, thousands separators,
  partial amounts as "300 מתוך 600" (never "300/600", which reads backwards
  in RTL).
- Status colors come from the design system's `tokens.json` exactly: paid
  `#6db283`/`#2b7247`, partial `#ee9a45`/`#9a5a12`, missing `#e07a70`/`#a8423b`.
- Auth: Clerk, Google sign-in only, single user (shapirado@gmail.com).

## Review Focus

- A recorded payment whose amount doesn't cleanly match the sum of the
  selected child/month dues (over- or under-paid) must still be stored
  exactly as entered — never silently reallocated, rounded, or rejected.
- A child with no price row covering an earlier month (joined mid-year, or
  price history starts after their enrollment) must not crash the due
  calculation or invent a due for a month with no price on record.
- A single month with two receipt lines (e.g. a partial payment followed by
  a top-up) must sum toward that month's paid total, not just reflect
  whichever line was recorded last.
- Setting a new price effective from a given month must only change dues
  from that month forward — never rewrite the due amount of an earlier,
  already-computed month.
- A malformed, empty, or unexpected-shape Morning webhook payload must
  still be captured as a `needs_review` receipt — the endpoint must never
  throw away or lose a payload it can't yet parse.

## Task 3: Due computation core logic

**Files:**
- Create: `src/lib/dues.ts`
- Test: `src/lib/dues.test.ts`

**Interfaces:**
- Consumes: nothing (pure functions, no DB).
- Produces:
  `type ChildPriceRow = { amount: number; effectiveFrom: string /* 'YYYY-MM-01' */ }`,
  `type ReceiptLineRow = { month: string /* 'YYYY-MM-01' */; amount: number }`,
  `priceForMonth(prices: ChildPriceRow[], month: string): number | null`
  (null when no price row covers that month),
  `type MonthStatus = { month: string; due: number; paid: number; status: 'paid' | 'partial' | 'missing' }`,
  `computeDueStatus(enrollmentStart: string, prices: ChildPriceRow[], lines: ReceiptLineRow[], asOfMonth: string): MonthStatus[]`
  — one entry per month from `enrollmentStart` to `asOfMonth` inclusive,
  skipping any month `priceForMonth` returns `null` for. Used by the
  dashboard (Task 6) and year view (Task 10).

- [ ] **Step 1: Write the failing tests**

```ts
test('a fully paid month is status paid', () => {
  const result = computeDueStatus('2026-11-01',
    [{ amount: 300, effectiveFrom: '2026-09-01' }],
    [{ month: '2026-11-01', amount: 300 }], '2026-11-01');
  expect(result).toEqual([{ month: '2026-11-01', due: 300, paid: 300, status: 'paid' }]);
});

test('a partially paid month is status partial', () => {
  const result = computeDueStatus('2026-11-01',
    [{ amount: 300, effectiveFrom: '2026-09-01' }],
    [{ month: '2026-11-01', amount: 150 }], '2026-11-01');
  expect(result[0]).toMatchObject({ due: 300, paid: 150, status: 'partial' });
});

test('two receipt lines in the same month sum together', () => {
  const result = computeDueStatus('2026-11-01',
    [{ amount: 300, effectiveFrom: '2026-09-01' }],
    [{ month: '2026-11-01', amount: 150 }, { month: '2026-11-01', amount: 150 }],
    '2026-11-01');
  expect(result[0]).toMatchObject({ paid: 300, status: 'paid' });
});

test('a price change only applies from its effective month forward', () => {
  const result = computeDueStatus('2026-10-01',
    [{ amount: 300, effectiveFrom: '2026-09-01' }, { amount: 330, effectiveFrom: '2026-11-01' }],
    [], '2026-11-01');
  expect(result).toEqual([
    { month: '2026-10-01', due: 300, paid: 0, status: 'missing' },
    { month: '2026-11-01', due: 330, paid: 0, status: 'missing' },
  ]);
});

test('a month before any price row covers it is skipped, not a phantom due', () => {
  const result = computeDueStatus('2026-09-01',
    [{ amount: 300, effectiveFrom: '2026-11-01' }],
    [], '2026-11-01');
  expect(result).toEqual([{ month: '2026-11-01', due: 300, paid: 0, status: 'missing' }]);
});
```

- [ ] **Step 3: Implement `priceForMonth` and `computeDueStatus` in `src/lib/dues.ts`**

`priceForMonth` picks the price row with the latest `effectiveFrom` that is
`<= month`, or `null` if none qualifies. `computeDueStatus` iterates every
calendar month from `enrollmentStart` to `asOfMonth`, skips months where
`priceForMonth` is `null`, sums matching `lines` per month, and classifies
`paid === due` as `'paid'`, `0 < paid < due` as `'partial'`, else
`'missing'`.

## Task 9: Morning webhook receiver and receipts-to-review

> **Amendment (controller ruling, post-planning):** Morning's real webhook
> docs were found (https://developers.morning.co/api) — the "unknown
> payload" assumption behind this task's original two-step plan no longer
> holds. Webhooks are configured in Morning under Developer Tools →
> Webhooks (per-event, with an optional signing secret), not blocked. The
> relevant event is `document/created`, delivered with header
> `x-webhook-topic: document/created`; we only care about documents where
> `type === 320` (חשבונית מס / קבלה — a receipt). Confirmed payload shape
> (matches the real PDF receipt #1564 the user captured): `recipient.name`
> is the single string `"<payer name> (<child name>)"` (e.g.
> `"צפי ברנר (עמליה)"`); `items[]` has one entry per month covered, where
> `items[].description` is the Hebrew month name (e.g. `"אוקטובר"`),
> `items[].sku` is `"חוג אומנות"`, and `items[].price`/`items[].quantity`
> give that line's amount; `total` is the document grand total (incl. VAT);
> `date`/`createdAt` give the document date. When a secret is configured,
> deliveries carry `x-webhook-signature`: HMAC-SHA256 of the **raw** body
> bytes, hex-encoded — verify over the raw bytes before any JSON parsing
> (re-serializing breaks it). Acknowledge with any 2xx status; anything
> else (including 3xx) counts as a failed delivery, and Morning disables
> the webhook after 15 consecutive failures.
>
> This upgrades the task from "store raw, parse later" to "parse for
> real now, still store raw as a fallback/audit trail": implement real
> extraction of recipient name → payer/child split, per-item Hebrew month
> name → `YYYY-MM-01`, and per-item amount → a `receipt_lines` entry,
> using `payer_name_aliases` (Task 4) to resolve the payer and a
> straightforward child-name match within that payer's children for the
> child; anything that doesn't resolve confidently (new payer, ambiguous
> child name, non-320 document type, missing/invalid signature when a
> secret is configured) still falls back to `needs_review` with the raw
> payload stored, exactly as originally planned. This also means
> **Global Constraints gains one item**: a configured webhook secret is
> read from `MORNING_WEBHOOK_SECRET` (env var) and every delivery's
> signature must be verified before any processing, over the raw request
> bytes, in constant time.
>
> **Second amendment:** also subscribe to and handle `client/created`
> (payload: `name`, `phone`, `mobile`, `emails[]`, per the same docs) —
> whenever Dalia/the user creates a new client in Morning, this fills in
> payer contact info automatically instead of waiting for it to be added
> "as we go." Keep this simple and conservative: match the event's `name`
> against an existing `payers.display_name` by exact (trimmed) equality;
> on a match, update that payer's `phone`/`email` (prefer `mobile` over
> `phone` if both present, first entry of `emails[]`) — never overwrite a
> phone/email that's already set with a different one (first write wins;
> this is a convenience fill, not a sync). No match → no-op (log and
> move on); do not auto-create a payer from this event alone, since not
> every Morning client is necessarily one of Dalia's payers. No new table
> for this — it's a small addition to the same webhook route and `src/lib/morning.ts`.
